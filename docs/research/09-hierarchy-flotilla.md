# Hierarchical axes: what flotilla's tables need

What do flotilla's tables need from hierarchical axes, and what has flotilla already decided? This note answers the research ticket [#180](https://github.com/flotilla-org/binnacle/issues/180) for the map [Hierarchical axes (#177)](https://github.com/flotilla-org/binnacle/issues/177), and feeds its grilling tickets: the View Spec (#181), who computes subtotals (#182), how a hierarchical item reaches the Grid (#183), expand and collapse (#184) and the data-driven column axis (#185). Terms follow [`CONTEXT.md`](https://github.com/flotilla-org/binnacle/blob/main/CONTEXT.md).

## Summary

- **No grouped, subtotalled or pivoted table is planned in flotilla.** ADR 0067 says so in as many words, and only keeps the wire vocabulary from ruling them out: a row's key need not be a stored primary key ("group and subtotal rows are keyed by group paths"), and a view's columns may change while it is live ([ADR 0067 §16.9](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0067-tables-describe-themselves-on-the-wire.md#L170)). binnacle asked for exactly those two openings in #3427, and the owner accepted them.
- **Hierarchy *between* tables is a navigation stack, not a tree.** ADR 0012 rules "Hierarchy is a navigation stack, never a tree-in-table", and ADR 0067 keeps one wire table per stored table, with child tables reached by drilling (a filter on the parent key). binnacle's hierarchical axes are for grouping *within* one table; flotilla does not want parent and child records shown as tree data.
- **Where flotilla groups today, it is either the server computing counts or a client deriving groups from flat facts.** The awareness named query is grouped and counted on the server (`AwarenessGrouping::Project` or `Convoy`, chosen by query parameter). The PM rail derives its tree on the client from flat entity facts through declarative, switchable level templates (#950). Neither is a binnacle table yet.
- **The one concrete table wish is "group convoys by project?"** in a parked brainstorm (#2633), next to "attention first" sorting and structured filters. It needs the owner live in the TUI.
- **The shipped wire carries no hierarchy.** Rows are flat `{field: value}` maps keyed by a tuple of natural-key values; the schema arrives once in the `table` message; there is no depth, group, aggregate or synthetic marker, and no message that changes the column set short of a `resync` and a fresh `table`.
- **The condition grammar is narrow:** `<field-path> <operator> <literal>` with six comparison operators, clauses ANDed, and no OR, IN or text search yet. Today's resource tier pushes down `==` only. A clause the store cannot push down is refused, never answered by listing and filtering. Nothing filters on an aggregate (`HAVING`).
- **Large grids get server-kept views by position** (ADR 0067 §15): a table, its `where` clauses, a sort and a window, kept as a B-tree with subtree counts on the server. It is not built yet (#3447, blocked on the WebSocket carrier #3249). Its request has no slot for grouping, aggregates or expand state; any server-computed grouping would need them there, because positions depend on them.
- **Small tables are fetched whole and handled by binnacle's In-Memory Table Source** (ADR 0067 §15, last bullet). For the inspector's first tables, grouping in the In-Memory Table Source needs nothing from the wire.
- **Decisions binnacle should follow rather than reopen:** meaning on the wire and layout in the viewer; keys made on the client by interning natural keys; composite keys as canonical CBOR tuples; roles never guessed from names and added as field properties; capabilities described per field; nulls lowest and text by code point; push down or refuse. From the rail: grouping is derived from flat facts by an ordered list of levels, switchable at runtime, with no expression language.

## Which views flotilla wants, and who computes them

### Tables: flat, with drilling

ADR 0012 decided flotilla's table layer in July: "Flat tables; **Enter drills** into a scoped table (drill target declared per kind, scope taken from the parent selection); Esc pops; breadcrumbs show the path. One cursor regime", with a Miller-columns cascade as a later layout over the same stack ([ADR 0012 L38-L47](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0012-tables-are-the-consumer-side-view-layer.md#L38-L47)). The reason given is the "#664 focus-trap class", which one cursor regime "structurally excludes". ADR 0067 carries the same shape onto the wire: "Each stored table is its own wire table", child rows carry the parent's key as a foreign key, and "A viewer drills by asking for the child table filtered to the parent's key ... This is ADR 0012's navigation stack, and it matches binnacle's flat grid." Nesting child rows in parent rows is rejected because it "falls back to an untyped `object` column and loses the description" ([ADR 0067 §4, L51-L57](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0067-tables-describe-themselves-on-the-wire.md#L51-L57)).

The TUI does this today: a convoy table drills into a vessel table, never into indented rows ([`table_view.rs` L646-L658](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-tui/src/table_view.rs#L646-L658)). Its only summary row is a note, "N older finished convoys hidden", computed in the client from rows it holds back ([`table_view.rs` L494-L505](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-tui/src/table_view.rs#L494-L505)).

The open wish list for TUI tables is #2633 (parked as a brainstorm, 2026-10-17). It asks, among default views: "Group by project? Should 'needs attention' float to the top?", plus multi-key sorts and structured filters on phase, project, host, attention, crew state and subject, and leaves open whether named queries should take filter and sort parameters so large result sets are trimmed on the daemon. It is marked as needing the owner live in the TUI. That is the only place a grouped *table* is asked for.

### The awareness band: server-side groups with counts

ADR 0018 defines the awareness band (sidebars, latents) as responses that "are trees: **grouping nodes** (convoy: label, summary counts, convoy-scope refs) containing **entries** (vessels/crews ...)", with "Runtime-switchable grouping (by project / convoy / host / attention)" as "a different join over the same facts", and grouping-header display details as surface config ([ADR 0018 L87-L93, L104-L108, L123-L136](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0018-presentation-attention-demands-regards-projection.md#L104-L136)).

In code this is the `Awareness` named query. The grouping is a query parameter, `AwarenessGrouping::{Project, Convoy}` ([`result_set.rs` L532](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-protocol/src/result_set.rs#L532)), with a limit on groups and entries per group (L539). The daemon's projection computes the groups, keys them by path-like ids (`convoy/<ns>/<name>`, `repo/<repo>`, `unparented`) and rolls up `AwarenessCounts` (total, active, waiting, done, ...) and a strongest state per group ([`awareness_projection.rs` L56-L60, L341-L365](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-projections/src/awareness_projection.rs#L341-L365); [`result_set.rs` L629, L700-L737](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-protocol/src/result_set.rs#L700-L737)). So this is a server-computed, one-level grouping with subtotals, of the "two queries, one re-aggregating" kind the map mentions.

Since #3592 (`b85e7b40`, 2026-10-20), `AwarenessNode` derives `Describe`, and its `entries` are `#[shape(child)]`. On the table wire the awareness tree therefore arrives as a root table of groups and a child table of entries, which a viewer joins by drilling: the same parent-and-child shape as stored kinds, not a hierarchical axis.

### The PM rail: client-side groups from flat facts

The richest grouping flotilla has is the presentation manager's rail, not a table. The owner's rulings on #950 (2026-07-24, via the map #969) are:

1. "Entities only on the wire. Group targets disappear entirely ... A rendered group header IS the template rendering the entity whose facts match that level."
2. "Grouping templates are declarative KDL, named and switchable. A template = ordered `level key=…` list with per-level options (label-key, collapse-single-member, show-empty) plus an entity filter clause ... No expression language." Entities missing a level's fact "file truthfully at the nearest present ancestor".
3. Single-member-group collapse is display policy in the template layer, and "Switching grouping template re-groups live without producer changes".

#969 records the attention roll-up the same way: "spine rollup is structural (renderer, max+count, template-controlled)". ADR 0051 later kept "Group paths ... for the containment tree that managers use for layout" alongside the entity facts ([ADR 0051 L84](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0051-presentation-metadata-entities-subject-edges-readiness-roles.md#L84)). Here the client computes groups and roll-ups over a set it already holds.

### Other aggregation on the server

The observed state diagram groups a kind's `log` rows by `(from, to)` and counts them, per request, as SQL on the server ([ADR 0067 §11](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0067-tables-describe-themselves-on-the-wire.md#L115-L123)). It is rendered as a diagram, not a table, and #3601 already flags its cost: "a full GROUP BY over the log view on every request". This is the only `GROUP BY` behind the table routes.

### Who computes, so far

Inferred from the above, not ruled anywhere for tables: flotilla computes aggregates over stored data on the server (awareness counts, diagram counts), and lets clients group what they already hold (the rail). ADR 0067 §12's rule that a filter the store cannot push down "is refused ... never answered by listing and filtering" suggests that a grouped view of a *large* table would also be computed by the server, not by the client listing and grouping. For small tables fetched whole, the client groups.

## What the wire says, and does not say

**The shipped message vocabulary** ([`table.rs`](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-protocol/src/table.rs), [`table.cddl`](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-protocol/src/table.cddl)) is `table`, `rows`, `synced`, `upsert`, `delete`, `progress`, `resync` and `count`. A row is `{* tstr => any}`, a flat map from field name to value. A key is `[* any]`, "canonical deterministic CBOR tuple; natural keys only". The schema is Frictionless (`fields`, `primaryKey`, open extra properties) and arrives in the `table` message. Nothing marks a row as a group, a subtotal or synthetic, nothing gives a depth or a parent, and nothing changes the column set mid-stream except `resync` followed by a fresh `table`.

**What ADR 0067 promises beyond that:**
- §16.9, quoted in the summary: keys are not assumed to be stored primary keys, and a view's columns may change while it is live. No message for a column change is designed.
- §16.4: "Composite keys have one encoding: the ADR 0063 deterministic CBOR of the key tuple. Equal keys always intern to the same binnacle Key." ([L165](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0067-tables-describe-themselves-on-the-wire.md#L165))
- §6: roles travel as field properties, come "from structure first, then from attributes", and "are never guessed from column names" ([L66-L70](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0067-tables-describe-themselves-on-the-wire.md#L66-L70)). The roles in code are open strings: `key`, `ref`, `time`, `sequence`, `state`, `since`, `transition-from`, `transition-to` ([`layout.rs` L142-L170](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-schema/src/layout.rs#L142-L170)). There is no aggregate or group role; one would be an additive property.
- §16.2: fields describe whether they can be sorted and which `where` operators they take (`sortable`, `whereOperators`), so a viewer can disable a control up front ([`table-http-api.md` L52-L54](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/table-http-api.md#L52-L54)). Nothing says whether a field can be grouped by or aggregated.
- §16.3: null is the lowest value, text sorts by Unicode code point, and a browser sort must agree with the server's.
- §15: the view subscription. A client subscribes to "a table, its `where` clauses, a sort and a window of positions"; the server sends the count, the window's rows, changes as positions, count changes and Locate answers, keeping "each live view as an in-memory ordered index of its keys, a B-tree with subtree counts" ([L146-L158](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0067-tables-describe-themselves-on-the-wire.md#L146-L158)). Implementation is #3447, blocked on #3249. The HTTP watch, by contrast, "follows the **whole filtered table**" and is not positional ([`table-http-api.md` L59-L62](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/table-http-api.md#L59-L62)).

**The condition grammar's limits.** A condition is `<field-path> <operator> <literal>`, with the operators `==`, `!=`, `<`, `<=`, `>`, `>=` and nothing else ([`condition.rs` L19-L26](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/crates/flotilla-address/src/condition.rs#L19-L26)). Repeated `where` clauses are ANDed; "OR, IN and text search are additions to the grammar, not to the routes" ([ADR 0067 §12, L125-L131](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0067-tables-describe-themselves-on-the-wire.md#L125-L131)). As shipped, the resource tier pushes down `==` only, the decided store all six on scalar fields, and anything else returns `unsupported_filter` ([`table-http-api.md` L45-L53, L95-L99](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/table-http-api.md#L95-L99)). #3601 notes every scalar column still advertises `==`. For hierarchy this means:
- binnacle's OneOf, `not` and Text Query Conditions have no wire form yet (OneOf needs IN, Text Query needs text search).
- There is no way to filter on an aggregate (`HAVING`), nor on a group as such. Filtering to one group is possible only as a leaf filter on the grouping field (`.project == flotilla`), which is also how drilling works.
- Field paths address one row's fields; nothing addresses a group's aggregate.

## Where binnacle's Table Source would carry hierarchy

The TypeScript Table Source (the outcome of binnacle#47) is per axis: `count`, `window(start, end)` returning Ids, `locate`, optional `distinct`, `unmatched` and `move`, with `idKey` mapping a host Id to a primitive, and `view(spec)` returning the View Spec applied; `cells(rows, cols)` returns values ([B `web/src/source.ts` L297-L382](https://github.com/flotilla-org/binnacle/blob/7f4a29f1e5df9045ec4d0aa6bc4bcafdf18706c1/web/src/source.ts#L297-L382)). The Rust View Spec is one `AxisView` per axis, a Filter Spec, a Sort Spec and hidden Keys ([B `view.rs` L213-L241](https://github.com/flotilla-org/binnacle/blob/7f4a29f1e5df9045ec4d0aa6bc4bcafdf18706c1/crates/binnacle-core/src/view.rs#L213-L241)). A server-backed source over ADR 0067's view subscription maps `count`, `window`, `locate` and Change Notices onto §15's messages one to one. Hierarchy would touch it at these points (all inferred; none is designed on either side):

1. **The request.** The View Spec is what a server-backed source turns into a view subscription. A grouped or pivoted view adds grouping fields, aggregates and, for a pivot, the column-axis split, and the subscription has no slot for them. Whatever #181 puts in the View Spec has to become a field of §15's request.
2. **Expand state.** If the server keeps positions (§15), positions depend on which groups are open, so expand and collapse are part of the request too, or the server cannot answer `count`, `window` or `locate`. For a client-grouped small table this stays in the In-Memory Table Source. This bears on #184.
3. **Identity.** Group and subtotal rows are keyed by group paths (§16.9). With §16.4, a group path encoded as a canonical CBOR tuple interns to a stable Key through the Key Interner, so a group's Key survives a re-sort and a window refetch. A group path and a leaf's primary key can be equal tuples; a tag that tells them apart is needed (inferred). This bears on #183.
4. **What a windowed item is.** `window` returns bare Ids and `cells` returns values. A grouped axis also needs, per item, whether it is a group, its depth, whether it is open and how many children it has. That is either a richer window answer or a per-item call like `unmatched`, and on the wire a row property the vocabulary does not have.
5. **Change Notices.** A leaf inserted into a closed group changes only that group's aggregate cells (`ContentChanged`); into an open group it is `Inserted` at a position. The server's ordered index has to produce both. The `count` message (§16.5) then counts what is shown, groups plus open leaves, which differs from the leaf count that Totals reports.
6. **The column axis.** binnacle already treats columns as an axis with `count`, `window` and `locate`. flotilla's wire sends columns only as the schema in `table`, all at once, and a change of columns only after `resync`. A pivot's data-driven columns need either a column window in the view subscription, with position changes like rows, or a full re-description on every change. §16.9 permits columns changing live but designs no message. This bears on #185.
7. **Capabilities.** binnacle asks `support(by)` per item; ADR 0067 describes `sortable` and `whereOperators` per field. "Groupable" and "aggregates allowed" would be more of the same field properties.

For small tables, none of this crosses the wire: ADR 0067 keeps "A small table can still be fetched whole and sorted by binnacle's in-memory source", so grouping and subtotals in the In-Memory Table Source are enough for the inspector's first grouped views.

## Decisions binnacle should follow

These are taken in flotilla and should constrain the map rather than be reopened:

- **Meaning crosses the wire; layout does not** ([ADR 0067 §1, L31-L33](https://github.com/flotilla-org/flotilla/blob/205128cae34140323fa43f7286b2cf970a43f9d8/docs/adr/0067-tables-describe-themselves-on-the-wire.md#L31-L33)). Where a subtotal row sits (top or bottom), header labels and which groups a user has open are viewer state. Which fields to group by and which aggregates to compute are part of the query, like sort and filter. (The split is inferred; the rule is ruled.)
- **Between tables, drill; do not nest** (ADR 0012, ADR 0067 §4). binnacle's hierarchy is grouping within one table's rows or columns. Parent and child records stay separate tables for flotilla; tree data over child tables is not what flotilla wants.
- **Keys are made on the client** by interning natural keys (§9), and **composite keys are canonical CBOR tuples** (§16.4). Group Keys should be built the same way from group paths.
- **Synthetic rows and live columns are allowed** (§16.9): binnacle need not pretend groups are stored rows, and a pivot's columns may come and go.
- **Roles come from structure, are never guessed from names, and are added as field properties** (§6). Marking a column as an aggregate or a row as a group belongs there, additively.
- **Capabilities are described per field** (§16.2); grouping capabilities should be too.
- **Ordering is fixed:** null lowest, text by code point (§16.3). Group order should follow it, so a client-grouped and a server-grouped table agree.
- **Push down or refuse** (§12). A source that cannot group or aggregate on the server says so; it does not list everything and group in the router. binnacle's `view` already returns the part of a spec it applied.
- **A view lives as long as its subscription, and the server caps views per connection** (§15). Grouped views add to that cost per view, not per store.
- **From the rail (#950), as precedent rather than rule for tables:** grouping is derived from flat facts, never stamped; a grouping is an ordered list of levels with per-level options (label, collapse a single-member group, show empty), switchable at runtime without changing producers; no expression language; an item missing a level's value files at the nearest present ancestor; and roll-ups such as attention are "max+count", computed by the renderer.

## Open questions for the grilling tickets

- **#181:** does the View Spec's grouping part look like the rail's level list (ordered keys, per-level options), and does it travel as part of §15's request?
- **#182:** for flotilla, aggregates over large tables are server-side by every precedent above; does binnacle need a mixed mode, a server that groups and a client that re-aggregates, for anything flotilla has? Nothing found suggests it does.
- **#183:** a group Key's encoding (tagged canonical tuple), and where depth and group-ness ride in a window answer.
- **#184:** whether expand state belongs in the request (server positions) or only in the In-Memory Table Source (small tables).
- **#185:** whether the column axis gets its own window and position changes in §15, or a pivot re-describes the table on each column change. flotilla would have to amend ADR 0067 for the first.
- **For flotilla, not binnacle:** ADR 0012's "never a tree-in-table" was aimed at nested records and the #664 focus trap. Whether a grouped convoy table (#2633) counts as one is the owner's call, and would be an ADR 0012 amendment if so.
